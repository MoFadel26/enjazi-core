# ADR-0012: Feel — motion, optimistic tasks, skeletons, the keyboard layer

**Status:** accepted
**Date:** 2026-09-25

## Context

After Phase 7 the app looked finished and felt inert. No element moved: the
theme had no transition anywhere. Ticking a task waited for the PUT and then
for the list's refetch before the box showed a tick. Every screen swapped
its content for a centred spinner while loading, so each load jumped the
layout. The streak, the product's reason to come back, was a flame and a
number. There was no keyboard path, the task list was one flat table where
renaming meant a modal, and the tasks empty state offered nothing to click.

Phase 8 fixes the response of the app rather than its look. The spec is
`docs/design.md`, sections "Motion", "Loading", "Keyboard" and the Tasks and
Dashboard entries under "Screens". The rule for this phase was to write as
little mechanism as possible: every moving part is a library already in the
stack or one from the same families.

The mechanisms, stated before the decisions:

1. **TanStack Query keeps every mutation in a cache, with its variables.**
   A mutation is `pending` from `mutate` until its `onSettled` resolves;
   `useMutationState` subscribes any component to the mutations matching a
   filter and returns what a `select` picks from each, such as the
   variables of every pending one, in the order they were made. Mutations
   that share a `scope` send their requests one at a time in that order;
   the rest wait, still pending. `onSuccess` runs before the mutation stops
   being pending, and the scope's next request starts only after
   `onSettled`. `setQueryData` writes a query's cached data and every
   subscriber re-renders; `cancelQueries` drops a fetch in flight so its
   answer is never written. The list's key is `['get', '/api/tasks']` —
   `openapi-react-query` omits the third element when a query has no
   parameters — and is read from `api.queryOptions('get', '/api/tasks')`
   rather than written out.
2. **Mantine animates in two ways.** Components that mount and unmount
   (`Modal`, `Popover`, `Menu`, `Tooltip`, `Spotlight`) run a `Transition`
   whose duration and easing come from `transitionProps`; stateful ones
   (`SegmentedControl`, `FloatingIndicator`, `Checkbox`) use CSS
   transitions from their stylesheet, some with a duration prop.
   `theme.respectReducedMotion` makes the `Transition`s run at zero
   duration when `prefers-reduced-motion: reduce` matches.
   `FloatingIndicator` measures a target element's box relative to a parent
   and moves one absolutely positioned element to it when the target
   changes.
3. **The `motion` library animates React elements declaratively.** An
   `m.*` element animates from `initial` to `animate` when it mounts;
   inside `AnimatePresence` it plays `exit` before it is removed from the
   DOM, rendered with its last props; with `layout` it animates to its new
   position when a sibling changes. The `m.*` elements carry no animation
   code of their own: `LazyMotion` supplies it as a feature bundle, which
   may be loaded with a dynamic `import()` after the first render.
   `MotionConfig` sets the default `transition` and, with
   `reducedMotion="user"`, drops transform and layout animation under the
   OS setting while keeping opacity.
4. **Spotlight is a store and a component.** `spotlight.open()` changes a
   store; `<Spotlight>` rendered once reads it and renders a `Modal` with a
   search input and the filtered actions. Its `shortcut` prop would bind
   `mod+K` through Mantine's `useHotkeys`; here it is `null`, and the app's
   own shortcut layer opens it. Closed, it renders no actions.
5. **`tinykeys` binds keys and sequences.**
   `tinykeys(window, { 'g t': f }, { ignore })` adds a `keydown` listener
   that tracks how far into each binding's sequence the keys so far have
   come, and forgets it one second after the last key. Within one map it
   stops at the first binding that fires, so the other bindings keep a
   half-matched sequence. Modifiers must match exactly, so `n` does not fire
   with Cmd held. `ignore` is a predicate over the event; the app passes its
   own.

## Decisions

### Motion comes from three libraries and one token file

`src/theme/motion.ts` holds the durations (fast 120ms, base 180ms, moment
700ms, linger 800ms), the one easing, the three offsets, and the same
durations in seconds for the `motion` library. Mantine's transitions read
them in `theme.components`, CSS colour transitions read the two variables
the resolver emits, and app animation reads them through `motion`. A screen
never writes a duration; `scripts/verify-phase-8.sh` fails on one, as Phase
7's script fails on a hex colour.

The library is loaded the way its documentation describes for bundle
size: `m.*` elements under `LazyMotion` with the `domMax` features (the
task rows animate layout, which `domAnimation` lacks), fetched by a dynamic
import after the first render. Measured with `vite build`: Phase 8 grew
the main chunk from 883 kB to 1,050 kB (318 kB gzip); after the split it is
967 kB (293 kB gzip), plus an 86 kB (28 kB gzip) chunk for the features.
The total is the same; the first render waits for less. An element that
mounts before the chunk arrives shows its end state without animating.

Rejected: *hand-written CSS keyframes in `global.css`.* The first draft of
this phase had three, with a media query for reduced motion. Exit
animation, a row moving between groups and the reduced-motion policy each
needed more code of the same kind; `motion` already does all three.
*`@formkit/auto-animate`.* Smaller, and it animates a list's children with
one hook, but it covers only lists; the points float and the flame would
still need keyframes. *Mantine's default durations.* 150 to 250ms, unnamed,
and different per component.

### Optimistic toggle, rename and delete for tasks, reversing ADR-0009

ADR-0009 rejected optimistic updates: "nothing here is latency-sensitive
enough". The tick turned out to be. It is the most frequent action in the
app and the one the streak hangs on, and it cost two requests before the
box changed. Updates and deletes now show at once, in TanStack's "via the
UI" form, applied to the whole app:

- The cached list only ever holds what the server said. `useTasks` returns
  it with every task update and delete still pending drawn on top, read
  through `useMutationState`, in the order they were made. The dashboard,
  the palette and the tasks screen all read `useTasks`, so all of them show
  the change.
- A write that fails stops being pending, so it stops being drawn. There is
  nothing to roll back; a notification says why.
- Updates and deletes share one mutation scope, so their requests reach the
  server one at a time, in order. Each success writes the server's answer
  into the cache before the next request is built, dropping any list fetch
  still in flight, whose answer may predate the write.
- `PUT` replaces the whole task, so an update's body is the server's copy
  of the task with only that update's fields changed, built when the
  request's turn comes. No request carries another write's prediction. This
  is why `useUpdateTask` uses TanStack's `useMutation` with the fetch client
  directly: `openapi-react-query`'s wrapper fixes the body when `mutate` is
  called. For the same reason the edit modal sends only the fields that
  were edited.
- The last write in the scope to settle reads the list again, for anything
  that changed on the server meanwhile. `onSettled` does not return the
  refetch, because the scope's next request waits for it.
- The streak is not predicted. It refetches after every update, and the
  points moment is read from the difference.
- Create stays as it was: the row needs the id the server assigns, and the
  modal already shows progress.

Rejected: *patching the cache in `onMutate` and rolling back on failure*,
TanStack's other form and this phase's first two versions. The cache then
holds predictions, and every rollback, snapshot and request body has to
reason about which of them are still pending. The review of this phase
found three ways a failed prediction still reached the server that way
(see "What the phase found"). *Optimistic updates everywhere.* Rooms,
events and settings are not tapped repeatedly, and the calendar already
moves the event first (ADR-0009).

### A completed task lingers, then leaves

With the change drawn at once, a task ticked in the Open view would vanish
in the same frame as its tick. It stays in its group, struck through, for
`durations.linger`, then leaves through `AnimatePresence`. The pause is
state in the tasks screen — a set of ids and a timer — because the exiting
element `AnimatePresence` keeps is the one rendered before the change,
which is the unticked row.

### Skeletons replace spinners on every screen

Each screen renders its frame and Mantine `Skeleton`s shaped like its
content while the query is pending. The spinner stays only where there is
no frame yet: the first `/me` and a lazy route's first fetch.

### The week row is derived from the run

`StreakResponse` has `currentLength`, `lastCompletedOn` and
`completedToday`; the API keeps the current run, not a log of days. The
last `currentLength` days up to `lastCompletedOn` are exactly the run, and
today is `lastCompletedOn` when completed today and the day after it
otherwise, so the row is exact for the run. Days before the run show empty
even if an earlier run covered them, and the spec labels the row as the
current streak for that reason.

Rejected: *a completion-day log in the API* (a table, a migration, a
contract change) for a seven-dot row. Worth it when a history view needs
it. *Deriving days from tasks' `completedAt`.* Wrong after a task is
reopened or deleted, both of which leave the streak as it was.

### The points moment reads the streak, not a constant

The Tasks header gains a streak chip. When the streak query's points rise
between two renders, the chip shows the difference floating up. Hard-coding
`+10` would copy `StreakService.PointsPerCompletion` into the browser. A
notification per tick was rejected as noise, and as one more line of text a
test's `getByText` could collide with.

### The keyboard layer is Spotlight and `tinykeys`

`@mantine/spotlight` is the palette: the same family and version as the
rest of Mantine, themed through `theme.components` like everything else.
`tinykeys` binds `n`, the `g …` sequences and `mod+K` in one layout hook,
one subscription per binding so no binding is left half-matched by
another, with one ignore rule for all of them: key repeats, IME composition, text
fields, editable elements, and anything inside an open dialog. A checkbox
or radio does not count as a text field, so ticking a task and pressing `N`
works. `mod+K` goes through the same rule rather than Spotlight's own
binding, which only looks at tag names: it opened the palette over an open
modal, and one Escape then closed both and dropped the draft.

Rejected: *`react-hotkeys-hook`*, this phase's first choice. Its default
filter treats every `<input>` as a text field, checkboxes included; its
`ignoreEventWhen` does not apply to sequences; and version 5.3.3 starts a
new sequence timer on every key without clearing the previous one, so a
`G` sequence begun within a second of an earlier `G` was dropped at random.
*`cmdk`* and *`kbar`*, unstyled palettes that would be themed by hand,
which is the second styling system ADR-0003 rules out. *Mantine's
`useHotkeys`*: it binds combinations, not sequences.

### `N` goes through the URL

`N` navigates to `/tasks?new`; the tasks screen opens its create modal when
the parameter is present and removes it on close. `?edit=<id>` does the
same for editing, which is how the palette opens a task.

Rejected: *a create-task modal owned by the layout behind a context.* A
second owner for a modal the tasks screen already owns. The URL form is
also a link that survives a reload.

### Tasks group by due date in the browser; the title renames in place

Grouping is applied to the one list response, like the filter (ADR-0009).
Clicking a title turns it into an input; Enter or blur saves through the
same optimistic update. The Edit modal stays for the other fields.

### Empty states may carry an action, amending ADR-0011

ADR-0011 kept actions out of empty states because a second "New task"
button broke the tests' strict mode. The constraint is the name, not the
action: Playwright matches role names as case-insensitive substrings, so the
tasks empty state says "Add a task" and the rooms one "Start a room". The
spec's test contract now lists the names and the rule.

## What the phase found

**A failed prediction could still be saved.** The first version patched
the cache and built each PUT body, which carries every field, when `mutate`
was called. Tick a task, rename it before the tick answers, and the
rename's body carried the tick's prediction; when the tick then failed, the
rename had already saved it. The browser test that found it holds one
request and fails it while the other passes. The second version queued the
writes and built each body at its turn from the patched cache minus later
patches, with per-field rollback. The review found that it still leaked:
snapshots taken while an earlier prediction was pending brought it back
after that one failed, a rollback cleared a later change to the same field,
the edit modal sent every field and so re-sent a pending tick, and a list
fetch answered mid-write replaced the patches and let the next body undo a
saved change. One case awarded streak points for a tick that had failed.
Each was reproduced against the real API. The third version, described
above, keeps predictions out of the cache altogether; the tests for all of
these cases are in `e2e/optimistic-queue.spec.ts`.

**Two overlapping ticks never refetched the list.** `onSettled` returned the
streak refetch, and TanStack keeps a mutation pending until its
`onSettled` resolves. The first tick to settle saw the second still in
flight; the second saw the first still waiting on its refetch; neither was
"last". `onSettled` now starts the refetches without returning them.

**The colour scheme sync cut every transition short.** `ColorSchemeSync`
called `setColorScheme` on every render of the layout, and Mantine's
`setColorScheme` injects `transition: none` on everything for a moment
while it switches. Before Phase 8 there were no transitions to cut; after
it, the sidebar marker and the mobile navbar never slid. It now calls it
only when the account's scheme differs from the current one.

**Mantine's reduced-motion support is per component.** `respectReducedMotion`
reaches every `Transition` and the `FloatingIndicator`, but the checkbox
tick kept its slide. The theme marks the tick with Mantine's own
reduced-motion attribute. The skeleton pulse and the button's loading
slide still run; the first is an opacity change the spec keeps, the second
is Mantine's and outside the Motion table.

**Some looks cannot be theme entries.** `SegmentedControl` renders a
`FloatingIndicator` for its own indicator, and theme styles are inline, so
styling the sidebar's indicator through the theme repainted the segmented
control too; the sidebar's look is a `:where()` rule in `global.css`.
`Spotlight` reads its styles from its own theme entry, not `Modal`'s, and
passes its own overlay. Its hover and selection, the skeleton's pulse
colour and NavLink's inactive hover (a fixed gray that matched the sidebar
in light mode, so hover was invisible) are in `global.css` as well, which
therefore holds more than ADR-0011's three rules.

**The first hotkey library did not fit.** `react-hotkeys-hook` skipped every
`<input>`, so ticking a task and pressing `N` did nothing; working around
that meant a predicate of our own, which its sequences then ignored; and
its sequence timer leaked, dropping quick consecutive `G` jumps. With our
own predicate needed anyway, `tinykeys` does the rest. One map for all the
bindings failed in its own way: `G T` then `G C` inside a second landed on
Tasks both times, because the map stopped at `g t` and left `g c` waiting
for a `c` after the first `g`. One subscription per binding fixed it; the
browser test presses the sequences back to back.

**The mobile navbar stayed open over a new screen.** It closed only from the
click handlers on its links, so a shortcut or a palette action changed the
route behind it. It now remembers the location it was opened at and is
open only while that is still the location.

**StrictMode replays mount animations.** A flame keyed on the streak length
with `initial={false}` popped on first load, because the development
double mount makes `motion` forget `initial={false}`. The pop is driven by
state set only when the length rises.

**A skeleton described by its control alone shifts the page.** The first
Settings skeleton drew a 36px bar per field and forgot the label above it;
the loaded sections were 21px and 43px taller. It is now measured against
the loaded form, and the spec describes label and control.

**The last row left without its exit.** When the last task left a view, the
empty state replaced the table in the same frame and `AnimatePresence`
went with it. The list and the empty state now switch inside their own
`AnimatePresence`.

**The calendar test depends on the hour.** `e2e/calendar.spec.ts` creates an
event at the next hour and drags it down two hours; between 22:00 and
midnight local time the drop falls off the grid and the test fails. It
predates this phase and is not changed here; the suite passes with
`TZ=UTC` at any hour.

## Consequences

- A duration, easing or offset is changed in `src/theme/motion.ts` and
  nowhere else.
- The tasks list cache holds only server answers. A new optimistic write
  to tasks joins the `task-writes` scope and is drawn by `useTasks`; a
  write elsewhere in the app follows the same shape with its own scope.
- Three dependencies are added: `@mantine/spotlight`, `motion` and
  `tinykeys`. `motion` is loaded through `LazyMotion`; a new animated
  element is an `m.*` element, and `strict` mode throws on a plain
  `motion.*` one.
- `src/theme/global.css` holds the rules listed above in addition to
  ADR-0011's.
- A button, link or label added anywhere must be checked against the test
  contract's names as substrings, not only as whole names.
- ADR-0009's rejection of optimistic updates and ADR-0011's rule against
  actions in empty states are superseded as described above.
