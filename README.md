# Enjazi Core

A productivity platform: tasks, calendar, collaborative rooms, streaks and an admin panel.

This is a ground-up rebuild. It shares a name and a problem domain with an
earlier Node/Express/MongoDB version, but no code and no git history.

## Status

Phase 4 — the API is complete and the frontend shell stands on it: login,
registration, logout, a protected app layout, and a typed client generated
from `openapi.json`. The screens themselves are Phase 5.

The API: cookie authentication, tasks, events, rooms and membership, settings,
and admin user management. `openapi.json` at the repository root is the
generated document the frontend client is built from.

| Endpoint | |
|---|---|
| `POST /api/auth/register` | creates an account and signs it in |
| `POST /api/auth/login`, `POST /api/auth/logout` | |
| `GET /api/auth/me` | the signed-in user and their roles |
| `GET POST /api/tasks`, `GET PUT DELETE /api/tasks/{id}` | the caller's tasks; 404 for anyone else's |
| `GET POST /api/events`, `GET PUT DELETE /api/events/{id}` | the caller's events; `GET` takes `from` and `to` |
| `GET POST /api/rooms`, `GET PUT DELETE /api/rooms/{id}` | rooms are listable by everyone; rename and delete need room admin |
| `GET POST /api/rooms/{id}/members` | members (members only) and join |
| `DELETE /api/rooms/{id}/members/{userId}` | leave, or remove a member as room admin |
| `GET PUT /api/settings` | the caller's settings tree |
| `GET /api/admin/users`, `GET PUT /api/admin/users/{id}` | Admin role only: search, page, disable, set roles |

Ownership of tasks, events and settings is enforced by global query filters in
`AppDbContext`, not by checks in controllers; [ADR-0006](docs/adr/0006-auth-and-ownership.md)
explains why. Rooms are shared and are the one deliberate exception;
[ADR-0007](docs/adr/0007-shared-data-admin-and-openapi.md) explains that, the
admin endpoints, and the OpenAPI document.

The first admin is made by setting `Bootstrap:AdminEmail` in configuration and
registering that address.

## Running locally

```sh
createdb enjazi_core
dotnet ef database update --project src/Enjazi.Api
dotnet run --project src/Enjazi.Api        # http://127.0.0.1:5180
cd src/Enjazi.Web && npm install && npm run dev   # http://127.0.0.1:5182
scripts/verify-phase-1.sh                  # schema check on a throwaway database
scripts/verify-phase-2.sh                  # integration tests, needs Docker
scripts/verify-phase-3.sh                  # the tests, then checks openapi.json is current
scripts/verify-phase-4.sh                  # typecheck, lint, build, browser tests against the API
```

Open the frontend at `127.0.0.1:5182`, not `localhost:5182`; `CLAUDE.md`
explains the cookie clash that motivates it. The dev server proxies `/api` to
the API, so the browser sees one origin. In Safari the sign-in cookie is
refused over plain HTTP; [ADR-0008](docs/adr/0008-frontend-shell.md) has the
detail and the fix.

`openapi.json` is regenerated by every build of the API. If an endpoint or
contract changes, the regenerated file belongs in the same commit, along with
`src/Enjazi.Web/src/api/schema.d.ts` from `npm run generate`.
`verify-phase-4.sh` fails if either is stale.

The tests bring up their own Postgres container and never touch the local
database. They run the test project directly rather than through `dotnet test`,
which the .NET 10 SDK cannot run a xunit.v3 project with; `verify-phase-2.sh`
has the detail.

The development connection string in `appsettings.Development.json` uses the
local Postgres.app defaults (no password, OS username).

This README describes only what exists. Planned work lives in `docs/plan.md`;
decisions and their reasoning live in `docs/adr/`.

## Local requirements

- .NET SDK 10
- Node 22+
- PostgreSQL 16+
- Docker, for the integration tests only
- Chromium via Playwright, for `verify-phase-4.sh` only; it downloads on first run
